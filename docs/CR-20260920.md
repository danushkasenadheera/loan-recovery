# Feature F1 — Search Loans by Loan Obtainer Name

## S1. Background

The dashboard finds a loan only by **Bank Code + Loan Type + 8-digit Loan Code**. Field officers often know the customer's name but not the loan code, and a customer may hold more than one loan. The client asked to search by the **name of the loan obtainer**, see the matching loans (obtainer name with loan number), and pick one.

## S2. Scope

In scope:
- A "search by name" mode on the dashboard loan search
- Live (as-you-type) results, one row per loan, ordered by obtainer name
- New read-only endpoint `GET /loan-search`
- Selecting a result opens the existing loan information card

Out of scope: changes to the code search or `LoanInfoCard`; closed/inactive loans; search by NIC/phone/address/member number; Head Office all-branch search (bank code required); any write operation or database change.

## S3. Decisions Recorded

| # | Decision | Chosen | Reason |
|---|---|---|---|
| D-1 | Trigger | Live typeahead (debounced) | Client preference |
| D-2 | Head Office scope | Bank code required | Name matching is a leading-wildcard scan; scoping to one bank keeps it fast |
| D-3 | Match type | Contains | Officers may know only part of the name |
| D-4 | Result layout | Flat list, one row per loan, ordered by obtainer name | Easy to scan and select |

Defaults assumed (not asked): active loans only (`Loan_status = 1`, same as `/loan`); name field only; results not stored in the URL.

# Feature F2 — Record a Visit Outside the GPS Range

## V1. Background

`components/loan-visit-recorder.tsx` enables **RECORD VISIT** only when the officer is near the loan's tagged location:

```
distance − min(accuracy, 30 m) ≤ 25 m      (effective limit up to ~55 m on poor GPS)
```

Findings from the current code:
- The check exists **only in the browser**. `POST /loan-visits` does not verify distance; it stores whatever `visitLat`/`visitLang` it is sent. The gate is therefore a UI control, not a server-enforced rule.
- Every visit already stores the officer's coordinates (`VisitLat` / `VisitLang`, `NOT NULL`), which the form requires before it will submit.
- If the range check cannot pass (poor GPS, wrong tagged location, customer at another address, no tagged location) the officer cannot record a visit at all.

The client wants to **keep** the current behaviour, but also **override** it, and have such visits **clearly marked** as recorded outside the range.

## V2. Scope

In scope:
- A separate secondary button to record a visit outside the range
- A stored flag on the visit and its display in the visit list and detail
- Server-side determination of the flag
- Visit GPS coordinates recorded for all visits (already the case; see V-FR-5)

Out of scope:
- Capturing a reason for the override (client: flag only)
- Recording when the phone has **no GPS fix at all** (coordinates remain mandatory)
- Manager approval of overridden visits, or role restrictions (any officer may use it)
- Rejecting or blocking any visit on the server
- Changes to the separate backoffice application (it can read the new flag; not built here)
- Retroactively re-evaluating existing visits

## V3. Decisions Recorded

| # | Decision | Chosen | Reason |
|---|---|---|---|
| D-5 | Entry point | Separate secondary button, shown only when RECORD VISIT is disabled | Keeps the normal path unchanged; overriding is a deliberate act |
| D-6 | Reason | None — flag only | Client preference |
| D-7 | No GPS at all | Coordinates still required | Avoids nullable coordinate columns and reporting changes |
| D-8 | Who can override | Any officer | Same access as normal visits |
| D-9 | Who decides the flag | **Server**, not the client | A client-supplied boolean can be forged or omitted, making the audit flag meaningless |
| D-10 | Loan has no tagged location | Visit is flagged | The range cannot be verified |
| D-11 | Confirmation | One-tap confirm before opening the form | Keeps the override deliberate without asking for typed input |

## V5. Functional Requirements

**V-FR-1 Override button.** A secondary button **"Record visit outside range"** appears below RECORD VISIT **only when RECORD VISIT is disabled** (out of range, GPS not ready or errored, or no tagged location). It is hidden when the normal button is enabled.

**V-FR-2 Confirmation.** Tapping it shows a confirmation: *"This visit will be marked as recorded outside the range."* Confirming opens the existing visit form; cancelling does nothing.

**V-FR-3 Same form.** The override reuses the existing Record Visit dialog and validation. No second form.

**V-FR-4 Coordinates required.** The override still needs a GPS position. If none is available, it stays unavailable with the message "GPS location required".

**V-FR-5 GPS recorded for every visit.** All visits (normal and override) store the officer's coordinates. Today the position is captured when the form **opens**, which can be minutes before Save. Proposed: re-read the position when the officer taps **Save Visit** (falling back to the opening position if the re-read fails). *(Proposed — see OQ-6.)*

**V-FR-6 Server sets the flag.** On `POST /loan-visits` the server sets

```
OutOfRange = OutOfRangeOverride
          OR loan has no tagged location
          OR haversine(visit position, loan tagged location) > 55 m
```

The 55 m limit is the client's 25 m target plus its 30 m accuracy allowance. The client does not send accuracy, so the server uses the fixed 55 m. Constants live in one server-side place and mirror `PROXIMITY_THRESHOLD` / `GPS_ACCURACY_CAP` in the recorder.

**V-FR-7 No blocking.** The server never rejects a visit for being out of range; it only flags it.

**V-FR-8 Display.** Visit list rows show an amber **"Outside range"** badge; the detail popup shows the flag and the recorded GPS coordinates. Normal visits show nothing extra.

**V-FR-9 Existing data.** Existing visits get `OutOfRange = 0` from the column default. They are not re-evaluated.

## V6. UI / UX

- Override button: `variant="outline"`, smaller emphasis than the yellow RECORD VISIT button; full width; same height (≥ 44 px).
- Confirmation: a small dialog with Cancel / Continue.
- Badge: amber, same style family as the existing distance badge; text "Outside range".
- The existing distance badge above the buttons remains unchanged.

## V7. Technical Specification

**Request** `POST /loan-visits` — existing body plus `outOfRangeOverride?: boolean` (default `false`).

**Responses** — list and detail DTOs gain `outOfRange: boolean`.

```ts
interface LoanVisitListItem { /* …existing… */ outOfRange: boolean }
interface LoanVisitDetail  { /* …existing… */ outOfRange: boolean }
```

**Server logic** (in `LoanVisitService.Create`): load the loan by `BankCode/LoanType/LoanCode` for `LoanAddressLat/Lang`; if either is null → flagged; else compute Haversine metres against the submitted `VisitLat/VisitLang`. A small shared helper avoids duplicating the formula.

**Schema:** one `BIT NOT NULL DEFAULT 0` column. The existing `SELECT/INSERT/UPDATE` grants on the table already cover it.

# Feature F3 — Interest Installments Paid Tile

> **Status:** the stored procedure is **done and deployed** and returns the new column **`NoOfInterestPaid`**. The API mapping and the web tile are not started. **No stored-procedure work is part of this CR.**

## I1. Background

The **View Loan Details** popup (CR-004) has a *Loan Summary* row of tiles. One of them, **Installments Paid**, is produced like this:

- The stored procedure `usp_GetLoanSummaryReport` calculates it: `ROUND(@TotalPrincipalPaid / @Loan_InsAmtLoan, 0)`, where `@Loan_InsAmtLoan` is the principal part of one installment.
- `LoanService.GetLoanDetailReport()` copies it unchanged (`NoOfInstallmentsPaid = summary.NoOfInstallmentsPaid`).
- `components/loan-details-modal.tsx` displays it.

It is therefore a **derived ratio**, not a count of payments. The client wants the same for interest. The stored procedure has now been updated to return it as **`NoOfInterestPaid`** (delivered script: `LoanRecovery SQL/CR20260920/LoanSummarySP.sql`, an `ALTER PROCEDURE` that adds the column as the **last** column of the result set). What remains is for the API to read that column and for the modal to display it.

## I2. Scope

In scope:
- API reads the SP column **`NoOfInterestPaid`** and exposes it in the loan detail report
- New tile between **Principal Paid** and **Interest Paid**
- Rename of the existing tile so the pair is unambiguous
- Layout change so all summary tiles fit on one row at desktop width

Already done (not part of this CR's remaining work): `usp_GetLoanSummaryReport` returns `NoOfInterestPaid`.

Out of scope: **any change to the stored procedure** (including the older repo copy `Docs/SP Loan Summary.sql`, which is left as is); other SP columns; `usp_GetLoanBalanceReport`; the payment history table; the visits-page "Arrears" figure (`usp_CalculateLoanBalanceRemain`); Android app.

## I3. Decisions Recorded

| # | Decision | Chosen | Reason |
|---|---|---|---|
| D-12 | Where the value is calculated | **In the stored procedure** (delivered) | Consistent with `NoOfInstallmentsPaid`; all summary logic in one place |
| D-13 | Formula (as delivered) | `ROUND(@TotalInterestPaid / @Loan_InsAmtInter, 0)`, 0 when the interest portion is null or 0 | Mirrors the principal formula; confirmed in the delivered script |
| D-14 | Placement | Between **Principal Paid** and **Interest Paid** | Client request |

## I7. Technical Specification

**Stored procedure — delivered, for reference only** (`LoanRecovery SQL/CR20260920/LoanSummarySP.sql`). Compared with the previous repo copy the only differences are this addition and the SSMS script header:

```sql
DECLARE @NoOfInssPaid INT = 0;
IF ISNULL(@Loan_InsAmtInter, 0.00) > 0
BEGIN
    SET @NoOfInssPaid = CAST(ROUND(@TotalInterestPaid / @Loan_InsAmtInter, 0) AS INT);
END
-- …
-- final SELECT, last column:
ISNULL(@NoOfInssPaid, 0) AS NoOfInterestPaid;
```

The internal variable is `@NoOfInssPaid`; **the output column name `NoOfInterestPaid` is what the API depends on.**

# Feature F4 — Show the Loan Note Type (Mode) on Loan Notes

> **Status:** design agreed; not implemented.

## N1. Background

The visits page has a **Loan Notes** accordion (`components/loan-visits-accordion.tsx`). It lists up to the 5 most recent notes for the loan, each with a date and remarks. The notes come from the table `U_tblLoanRecord`, read by `LoanService.GetLoanDetails()` and returned as `loanNotes` in `GET /loan-details`. This app only reads that table.

The client wants each note to also show its **type**. `U_tblLoanRecord.LoanRecord_Mode` holds it as an integer (never null); the text lives in the master table `M_tblLoanRecTypes`:

| Column | Type | Meaning |
|---|---|---|
| `ID` | `numeric(13,0)` NOT NULL | Matches `LoanRecord_Mode` |
| `lrDescription` | `varchar(80)` NULL | The text to display |

## N2. Scope

In scope:
- Read `LoanRecord_Mode` for each note and resolve it through `M_tblLoanRecTypes`
- Show the description on each note in the Loan Notes accordion
- A SQL permission grant for the new table (see N4)

Out of scope: filtering or grouping notes by type; changing which notes are selected (same filters, same 5, same order); the View Loan Details popup (it does not show notes); creating or editing notes or note types; the Android app.

## N3. Decisions Recorded

| # | Decision | Chosen | Reason |
|---|---|---|---|
| D-18 | Source of the text | `LoanRecord_Mode` → `M_tblLoanRecTypes.ID` → `lrDescription` | Client specification |
| D-19 | How it is looked up | A **separate, isolated query** for the (at most 5) distinct modes — not a join inside the notes query | Lets a failed lookup degrade without losing the notes |
| D-20 | Lookup failure | **Degrade and log:** notes are still shown, without the label, and a warning is logged | Client choice. A missing grant must not take the whole visits page down |
| D-21 | No matching row for a mode | Show the note without a label (assumed) | `LoanRecord_Mode` is never null, but an unmatched or unused type can still occur; a placeholder would clutter the note |
| D-22 | Null `LoanRecord_Mode` | Not handled as a case | Client confirmed the column is not null |
| D-23 | Display | Small label on the date line, next to the date | Keeps the remarks text unchanged and readable |

## N7. Technical Specification

**Data flow**

```
U_tblLoanRecord (LoanRecord_Mode)  ──►  M_tblLoanRecTypes (ID = mode, lrDescription)
        │ 5 latest notes                        │ one query for the distinct modes
        └────────────── combined in LoanService ┘  → LoanNoteDto { Remarks, Date, Mode }
```

**Service shape** (`GetLoanDetails()`)

```csharp
var notes = _dBContext.LoanRecords
    .Where(/* unchanged filters */)
    .OrderByDescending(r => r.LoanRecordDate)
    .Take(5)
    .Select(r => new { r.LoanRecordRemarks, r.LoanRecordDate, r.LoanRecordMode })
    .ToList();

var modeText = new Dictionary<decimal, string?>();
try
{
    var ids = notes.Select(n => (decimal)n.LoanRecordMode).Distinct().ToList();
    modeText = _dBContext.LoanRecTypes
        .Where(t => ids.Contains(t.Id))
        .ToDictionary(t => t.Id, t => t.Description);
}
catch (Exception ex)
{
    _logger?.LogWarning(ex, "Loan note types unavailable for loan {Loan}", $"{bankCode}/{loanCode}/{loanType}");
}

// each note: Mode = modeText.TryGetValue((decimal)mode, out var d) ? d?.Trim() : null
```

The mode is cast to `decimal` because `M_tblLoanRecTypes.ID` is `numeric(13,0)`.

**Contract**

```ts
interface LoanNote {
  remarks: string | null
  date: string | null
  mode: string | null   // new: lrDescription for LoanRecord_Mode
}
```

**Permissions.** The existing "notes" query already reads `U_tblLoanRecord`. `M_tblLoanRecTypes` is a different table; if the API's SQL login has no `SELECT` on it, SQL Server error 229 is raised. The isolated lookup turns that into "notes without labels plus a warning" (N-FR-4) instead of a failed page. The grant is still required for the feature to work.

# Feature F5 — Show Member Share in the Loan Details Section

> **Status:** **implemented** on 2026-09-20 (API lookup, DTO field, frontend type and display, unit tests). Not yet deployed. See the implementation result in `CR-Implementaiton-20260920.md` (F5.6).

## M1. Background

The visits page sidebar has a **Loan Details** section (an accordion item) showing the reference number, address and bank account. These come from `GET /loan-details`. Earlier versions of the page also showed the obtainer's name, NIC and phone numbers in a separate Customer card; the page has since been redesigned and that card no longer exists.

The client wants the obtainer's **member share** shown with the loan's address details. It is stored in `M_tblMember`:

| Column | Type | Note |
|---|---|---|
| `Member_Shere` | `numeric(19,4)` | The database spells it "Shere"; the screen label is "Member Share" |

The API already reads `M_tblMember` for guarantors, using `Member_StoresNO` = bank code and `Member_MemberNo` = the member number held on the loan (`Loan_Mem1`).

## M2. Scope

In scope:
- Return the loan obtainer's member share in `GET /loan-details`
- Show it in the Loan Details section of the visits page sidebar, directly below the address

Out of scope: guarantors' shares (client chose obtainer only); the View Loan Details popup; the dashboard loan card; editing or any write operation.

## M3. Decisions Recorded

| # | Decision | Chosen | Reason |
|---|---|---|---|
| D-24 | Whose share | The **loan obtainer** only | Client choice |
| D-25 | How the member is found | `M_tblMember` where `Member_StoresNO` = bank code and `Member_MemberNo` = `Loan.MemberId` (`Loan_Mem1`) | Same key the guarantor lookup already uses; scoped by bank code like every other query |
| D-26 | No value | Hide the row when there is no member row or the share is null; a real `0` is shown | Client choice; matches how the empty address and bank account rows behave |
| D-27 | Format | Currency like the other amounts on the page, `LKR 1,234.56` (2 decimals from the 4-decimal column) | Consistency; assumed (OQ-18) |
| D-28 | Label | "Member Share" | Readable; the database spelling is not shown |

## 10. Dependencies & Risks

| Item | Notes |
|---|---|
| **Release order (F2)** | Run the SQL script **first**, then deploy the API, then the web app. EF selects the new column in every visit query, so deploying the API before the column exists breaks all visit reads |
| Release order (F1) | API first, then web (per `Docs/RELEASE.md`); endpoint is additive |
| Proxy whitelist (F2) | `app/api/loan-visits/route.ts` forwards named fields only; a missed field means the override is silently ignored |
| Flag vs. legitimate visits (F2) | A visit allowed by the client using accuracy (up to ~55 m) could be flagged if the position drifts between form open and save; the Save-time re-read reduces this |
| Not a security control (F2) | The server flags but never blocks, so direct API calls remain possible; the flag is an audit aid, not enforcement |
| Threshold duplication (F2) | 25 m / 30 m live in both the recorder and the server; changing one requires changing the other |
| Performance (F1) | `LIKE '%text%'` cannot use an index; bounded by required bank code, 3-char minimum, debounce and 50-row cap |
| Load (F1) | Live search issues many small queries per officer; monitor after release |
| Test gaps | Unit tests run on in-memory SQLite, not SQL Server (collation, real data). GPS behaviour needs manual testing with browser location simulation |
| Existing script defect | `LoanRecovery SQL/visit-table-create.sql` has a stray `;` after the `Manager_Username` column inside `CREATE TABLE` and would not run as written. Not part of this CR; the new script uses `ALTER TABLE` and is unaffected |
| **Release order (F3)** | The SP is already updated, so the order is API → web. The API reads `NoOfInterestPaid` through `SqlQueryRaw` inside an empty `catch { }`: against a database **without** the updated SP the read fails silently and **the whole summary shows `—`** with nothing logged. The reverse (updated SP, old API) is harmless — the extra column is ignored |
| Name coupling (F3) | EF maps the SP result by column name. The API property must be exactly `NoOfInterestPaid` (not the SP's internal variable `@NoOfInssPaid`); a mismatch also fails silently. Covered by an explicit API check that the other summary fields still populate |
| Derived value (F3) | Like the principal count, this is a ratio, not a payment count. Interest paid in advance, part-paid interest, changed installment amounts or non-fixed interest will produce rounded or misleading numbers |
| Layout (F3) | 7 columns at `max-w-5xl` may overflow for large amounts; needs visual tuning |
| No automated coverage (F3) | No tests cover the summary and SQLite cannot execute stored procedures; verification is manual API and UI checks on real loans |
| **Missing permission (F4)** | The SQL login may lack `SELECT` on `M_tblLoanRecTypes` (SQL error 229). The lookup is isolated, so notes still display without labels and a warning is logged — but the feature does nothing until the grant is applied. Run the grant before the API release |
| Whole-page failure avoided (F4) | Reading notes runs inside `GET /loan-details`; a failure there returns 403/500 and the visits page shows "not found" for every loan. This is why the type lookup is a separate query with its own `try/catch` and not a join in the notes query |
| Null or non-int mode (F4) | If `LoanRecord_Mode` is nullable in the real database, EF fails reading the note (plain `int` property). Confirm the column definition (OQ-15) |
| Logger added to `LoanService` (F4) | Existing tests call `new LoanService(Db)`. The logger is an optional constructor parameter so they still compile; DI injects it in the API |
| Wrong member link (F5) | If `Loan_Mem1` is not the obtainer's member number the card shows another member's share or nothing. Confirm with real loans before release (OQ-17) |
| Precision (F5) | `numeric(19,4)` is read as `decimal` in the API but serialised as a JSON number; values beyond about 15 significant digits would lose precision in the browser. Not expected for shares |
| Column type not declared (F5) | `Member_Shere` is mapped without `HasColumnType("decimal(19,4)")`; EF logs a default-type warning at startup. Reads are unaffected; add the column type for consistency |
